43 · 项目拆分：让窗口不再承担全部业务

前置：第 42 章。目标：为 TaskDesk 的扩展建立清楚边界，避免一开始就堆设计模式。

从一次“新增任务”追踪职责

Window 读取输入并显示结果；应用服务组织“新增、刷新、错误反馈”的流程；仓储执行持久化；规则函数检查标题。小项目允许合并一些层，但应能说清每段代码负责什么。

TaskDesk 当前由 Window 与 TaskStore 配合，SQL 查询模型仍参与窗口。不要把教程中的目标架构说成现有代码已经全部实现；可以逐次抽离查询、导入、迁移服务，每次保持行为不变。

先提取纯规则

把标题校验整理为不依赖 QWidget 的函数，输入 QString，返回明确结果。例如区分空标题与超长标题，使界面能选择不同提示。规范化和校验顺序固定：trimmed → 空值 → 长度 → 保存。

UI 验证用于及时提醒，仓储边界验证防止其他调用路径绕过。为了避免维护两份规则，让 UI 调用共享规则，而不是分别写两个不同上限。

再提取流程，不急着做全局单例

服务通过构造函数获得仓储依赖，窗口通过服务发命令。这样测试可以替换数据源，业务类也不必自己弹 QMessageBox。错误作为返回值或信号向上交付，展示位置由界面决定。

对象之间先列清所有者和观察者。QObject 类可用父子关系；普通值类型优先按值保存；非 QObject 资源适合 RAII。不要为统一形式让所有类都继承 QObject，也不要把每个对象都放进 shared_ptr。

一次重构的具体步骤

  1. 记录原有新增、空值失败、排序后删除三个流程。
  2. 新建验证函数文件，加入 CMake 目标和测试。
  3. 让 TaskStore 调用它；保持返回行为，运行原测试。
  4. 让界面也调用它提供提前反馈，再运行手工流程。
  5. 删除重复规则，检查 include 方向：规则层不包含窗口头文件。

只有出现多个仓储实现或测试替身需求时再加抽象接口。接口不是越多越好，能减少变动传播才有价值。后续可将库目标导出给测试，避免测试依赖整套窗口启动。

验收：标题上限只需改一个规则入口；业务层不弹窗；异常或失败信息能到达用户；重构前后的数据文件仍可打开。参考答案要点：先保持行为，再扩展功能，一次提交做一件可验证的事情。
