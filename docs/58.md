# 58 · Qt 图形集成实战路线：嵌入、选型、性能与发布

## 一、先按应用需求选入口

| 需求 | 可以先选的路径 | 需要接受的责任 |
|---|---|---|
| Widgets 工具里显示 3D 视图 | QOpenGLWidget | 上下文、GL 状态、GPU 资源 |
| 独立 OpenGL 画布 | QOpenGLWindow | QWindow 事件与呈现路线 |
| Qt 管理窗口与交换链的 Vulkan 视图 | QVulkanWindow | 自建管线、资源、额外同步 |
| Quick 控件和动画界面 | Qt Quick 场景图 | 遵守场景图线程与资源生命周期 |
| 需要更底层跨后端抽象 | 研究 QRhi 等相应版本接口 | 确认版本稳定性与支持范围 |

Qt Quick 可以使用不同渲染后端，因此不能假设它的渲染线程里永远存在 OpenGL 上下文。将 OpenGL 代码嵌入 Quick 前先选择匹配的集成方式，不把 QOpenGLWidget 的 paintGL 直接复制为任意 QML 回调。

## 二、在 Widgets 中嵌入 QWindow

QWidget::createWindowContainer(window,parent) 可以把 QWindow 放进 Widgets，但会接管所嵌窗口的相关所有权，且涉及原生窗口的堆叠、焦点、裁切和性能限制。先阅读该接口约束，再做复杂滚动区、透明覆盖和大量容器。

本例 18_vulkan 是独立 QWindow。扩展到 TaskDesk 的渲染面板时，应先建立单独试验窗口，验证 Tab 焦点、快捷键、缩放和关闭顺序，再整合数据库业务；不要同时改变 UI 架构和渲染后端。

## 三、定义一个可测试的渲染器边界

业务层输出普通场景数据：顶点、相机、选择状态；渲染层消费这些数据并生成画面。按钮只改变状态，不直接管理 VkDeviceMemory。数据加载失败、图形环境不满足和用户取消，应分别显示原因。

推荐练习项目是一个模型观察器：第一步固定三角形；第二步矩形纹理；第三步相机交互；第四步离屏截图；第五步仅在需求成立时增加另一个后端。两个后端共享场景语义，而不是强求所有底层资源类型共用同一份代码。

## 四、性能比较不能只看 API 名称

用同一场景、相同分辨率与采样、相同驱动环境比较。CPU 帧准备时间、GPU 执行时间、呈现等待和总输入延迟分别测量；vsync 可能使两者都稳定在同一帧率，却隐藏 CPU/GPU 工作量差异。

先减少每帧创建资源、重复 shader 编译、无意义数据上传和过多小 draw，再研究多线程录制。Vulkan 的显式控制增加实现责任，小型 Qt 桌面工具不一定因为切换后端获得用户可见提升。

## 五、发布目录与图形驱动

windeployqt 收集 Qt DLL 与插件，不会替用户安装适合显卡的驱动。OpenGL 示例要带 Qt6OpenGL、Qt6OpenGLWidgets 等实际依赖；Vulkan 示例仍依赖运行环境可用的 Loader 和驱动。不要把本机 System32 的驱动 DLL 散拷到发布目录碰运气。

shader 文件若外置，应从明确路径或资源系统加载，缺失时提供日志；SPIR-V 与源码、编译目标版本一起管理。验证层只用于开发诊断，不强制绑到普通发布启动流程。

## 六、图形专项验收表

- 初始化失败时显示或记录明确原因，不进入使用空 handle 的绘制路径。
- shader 错误、资源缺失、窗口 resize、最小化恢复、反复打开关闭分别验证。
- 100% 与高 DPI 下视口比例正确，截图大小与目标像素尺寸一致。
- OpenGL 自检实际读回三角形像素；Vulkan 自检只说明其记录的帧检查范围。
- Vulkan 验证层是否开启、是否收到错误单独记录，不能从普通启动成功推断。
- 至少在另一台符合要求的机器验证分发包；未做的环境明确标注。
